# 目前的不足

如实、客观地列出项目当前的局限。按「适配性 → 硬件门槛 → 功能 → 工程 → 许可证」分组；每条都写清影响与现有的缓解措施（如有）。本文与 [validation.md](validation.md) 的「诚实边界」互为补充。

## 适配性

- **只在一台机器上完整验证过**。Fedora 44 + GNOME（Wayland）+ x86_64 + RTX 4080 是唯一实测环境；Ubuntu / Arch / Debian、KDE / X11 / sway、ARM 均未验证。缓解：`check-environment.sh` 环境预检、安装脚本多处降级容错，但没人实际跑过就是没验证。
- **内置 librime 二进制是 Fedora x86_64 的**（需 glibc ≥ 2.38），其他环境可能加载失败。缓解：引擎会自动回退系统 librime（装发行版的 librime 包即可），但该回退路径同样未在异构环境实测。
- **桌面集成 GNOME 优先**：输入源注册、全局热键、`environment.d`、`systemctl --user` 都按 GNOME 设计。其他桌面可手工集成（组件 XML + 桌面自己的快捷键机制），属于「理论可行、无人验证」。

## 硬件门槛

- **默认语音后端需要 NVIDIA GPU**：Qwen3-ASR 1.7B bf16 约需 4GB+ 显存。无 GPU 必须切云端后端（自备 API Key，音频上传服务商）或降级 vosk / 自定义命令——体验与准确率都会下降。
- **首次语音有明显的模型加载等待**：sidecar 冷启动 30 秒到数分钟（视盘速），之后才有常驻/预热。对「装完立刻想试」的用户不够友好。
- **MiMo 本地后端资源占用高**：作为可选大模型路线，显存/内存需求显著高于 Qwen3-ASR，普通消费级显卡不一定跑得动。

## 功能局限

- **语音热键格式受限**：`VOICE_IME_HOTKEYS` 解析只支持 `Ctrl+Alt+字母` 组合，不支持任意自定义组合键。
- **静音检测是简易电平方案，不是神经 VAD**：toggle 模式默认启用静音自动停止（约 2.5 秒静音自动结束、8 秒无声自动结束），但判据是录音电平阈值（RMS），嘈杂环境可能不触发、极安静环境可能误触发；fixed 模式的 VAD 同为阈值方案。
- **模糊音默认禁用**：rime-ice 原生支持，但实测开启后候选污染严重，出厂关闭；需要用户手动编辑配置再部署。
- **LLM 后处理被强制关闭**：实验结论是小模型改写会劣化听写原文（改词、吞字、添加不存在内容），因此引擎侧硬关闭；当前没有可靠的「润色不改写」方案，重排能力实际缺失。
- **没有软件包分发**：无 rpm / deb / flatpak / AUR，只能 git clone + `./install.sh`；升级 = git pull + 重跑安装脚本。
- **界面与文档只有中文**：引擎 UI 文案、README、日志提示均为中文，无 i18n。

## 工程局限

- **CI 无法覆盖端到端**：GitHub Actions 上没有图形会话与 IBus daemon，按键路由、候选框、输入源切换、语音全链路都没有自动化测试，回归靠作者手测。
- **无覆盖率映射**：`affected` 门禁只能退化为「变更文件语法检查 + 全量单测」，做不到精准的受影响测试子集。
- **单进程引擎 + Python**：引擎是单个 Python 进程（PyGObject 主循环），复杂度继续增长时（更多热键、更多 UI 状态）可维护性会受挑战；语音识别虽在独立 sidecar，但录音与后处理仍在引擎进程内。
- **云后端依赖外部服务演进**：MiMo Token Plan 与火山接口若变更，需要跟进维护客户端代码；密钥管理依赖 Bitwarden Secrets Manager（不用的用户需自行改造注入方式）。
